# Redstone

## Purpose

A redstone contraption can depend on update order, quasi-connectivity, and piston behavior. Represent connected contraptions as sets of chunks and keep each set under one owner. The real server coordinates these sets as ownership metadata; this is not a second simulation of offloaded redstone.

## Border-only connection detection

Chunk ownership is already indivisible, so the detector only needs dependency edges crossing horizontal chunk boundaries. Never scan a chunk's interior to discover a contraption. Inspect the two block columns immediately inside each edge: local block X/Z 0, 1, 14 or 15, over the dimension's build height. Corners belong to both adjacent bands. Both sides of a boundary supply the same two-column band; this is not a two-block radius scan of every component in the chunk.

Maintain a versioned dependency-rule registry for the exact Minecraft and mod set. A rule describes potential signal outputs/reads, notification targets, conductor behavior and structural/movement dependencies for a block's type, orientation and shape. Include legal powered/unpowered states and pending transitions, not only current signal strength. A missing required rule makes the affected boundary unresolved and its connected chunks server-owned until resolved. If the unsupported behavior's reach cannot be bounded, decline offloading for that world. Do not infer support from a matching JAR name.

### Boundary graph algorithm

1. On initial boundary load, read consistent completed-state band summaries from both sides, with chunk identity/version/generation. The real server indexes these summaries as topology metadata; the current simulator produces them without a second authoritative redstone tick. Missing or stale summaries cannot prove a safe disconnected edge. Keep ownership unchanged while refreshing them; do not grant a fragment of a possibly connected set.
2. Enumerate rule-defined directed potential edges between band positions in both directions. Each local connection check follows at most two adjacent block-to-block steps on an actual signal, read, update or movement dependency path. Use six-face adjacency, not a geometric radius of nearby components. Dust steps and virtual QC inputs use the explicit intermediate positions below. Do not turn arbitrary touching solid blocks into signal edges.
3. Compose the local checks through explicit conductor and virtual-QC nodes. This permits a complete source-to-mechanism dependency longer than two steps without widening the horizontal border band or scanning interior components. Preserve path kind: a notification is not proof of power, and potential QC power is not proof that the mechanism already received an update. If a required rule reaches outside the available bands, report the boundary as unsupported rather than silently shortening it or doing a deeper scan.
4. For ownership only, discard direction after collecting all dependency edges. Add an undirected chunk edge for every dependency spanning different chunks. All dependencies inside one chunk already have one chunk owner and need no interior connectivity search. Compute connected components of this chunk graph, including chunk edges already indexed on other borders. This transitive graph traversal reads cached boundary metadata, not every block of the interior or every block of every member chunk. The two-step local bound never caps the whole connected set.
5. For a change, retain the old band summary, construct the proposed new summary and recompute affected chunk-graph components for removals as well as additions. Before the triggering operation is allowed to join different owners, coordinate the complete resulting set under the consolidation rules below. Publish the new topology with its identified completed-state boundary; never leave a newly joined cross-owner dependency running while metadata catches up. A notification alone can require reevaluation even when no block was placed or broken.

### Dependency-rule requirements

The following are mandatory rule families. They define ownership dependencies, not a replacement redstone simulator; execution still uses the selected Minecraft/mod implementation and its original update order.

| Family | Required directed dependency checks |
| --- | --- |
| Six-face signal | For each face, connect a potentially emitting output to a compatible reading face. Preserve facing/attachment restrictions of sources, repeaters, comparators, torches and mechanisms. Evaluate possible active and inactive states without toggling the real world. A repeater/comparator output is not an omnidirectional source. |
| Conductors | For source `s`, conductor `c`, and receiver `r`, test `s -> c -> r` with the selected block's conductor and power predicates. Strong power can feed adjacent dust or mechanisms; weak dust power through a conductor can feed mechanisms and repeater/comparator inputs, not another dust line. Never propagate conductor-to-conductor power merely because the blocks touch. Record both supporting-block changes and power dependencies. Conductivity is the game's predicate, not visual solidity or opacity guessed from a name. |
| Dust | Include each allowed horizontal dust link, and ascending/descending dust link with its supporting block and clearance positions, following the selected version's connection/occlusion rules. Represent a one-up/one-across link as two adjacent steps through its corner position. Track potential changes to shape/support/clearance, not just lit dust or its currently drawn arms. Use the actual directed power faces for dust-to-mechanism/conductor checks. |
| Repeaters/comparators | Include rear input, side locking/comparison inputs and forward output with orientation retained. Comparator inventory/analog reads include their declared through-one-conductor path and relevant block-entity state. A container value change can change an edge's input without a placement. Preserve side-specific dependencies even while locked or unpowered. |
| Updates and observers | Record rule-defined neighbor notifications, attachment/support reevaluation and observer watched-face dependencies independently of signal edges. Include notifications through an attachment/conductor position when the selected component sends them. An observer can depend on a non-redstone block change; the watched block need not emit power. Do not infer that notifications propagate through an unlimited chain of arbitrary solid blocks. |
| Quasi-connectivity | For each piston, sticky piston, dispenser and dropper, create a virtual power-read node at the position immediately above it and a dependency from that node to the mechanism. Evaluate the version's eligible power reads into that node, including power through one conductor, whether its space is air, conductive or occupied. Follow actual piston face exclusions for direct reads. Capture notification dependencies separately; QC eligibility must not force immediate activation. A power source can be three adjacent steps from a mechanism through conductor plus virtual node. Compose the local checks, do not cut that dependency at two total steps. Do not assign QC to other mechanisms without a supported rule. |
| Pistons and moving blocks | Use the simulator's proposed move list, including piston base/head, pushed/pulled blocks and sticky attachments. Add cross-border dependencies for the affected source/destination positions and relevant power/update paths. Keep the operation deferred if those positions would join different owners. Moving a non-redstone block can change conductivity, dust support, observer input or QC. Do not inspect only the moved redstone components. |
| Mods and nonlocal behavior | Mods must supply all of the above dependencies they add or alter and a bounded reach. A supported nonlocal edge must be explicit in boundary metadata; the detector must not discover it by an interior scan. Without a rule that can establish the complete dependency from the permitted bands, leave the affected unit on the real server. |

The registry identity belongs in compatibility/topology metadata. Both endpoints must agree on it before offloading across an affected boundary. The family table does not claim that a native Minecraft 26.3 rule registry has already been implemented or exhaustively tested. Until its version-specific predicates and mod extensions are supplied and validated, affected boundaries are unsupported, not optimistically disconnected.

### Border changes and piston moves

Recheck only the affected horizontal border bands on band block placement/breaking, state/shape changes, support/conductor changes, or a rule-defined band input/update change. Interior-only work with no supported dependency reaching a band needs no connectivity scan. Ordinary simulation can report a change to a band dependency; this is not permission to start scanning the interior.

For a piston move, trigger a recheck when any moved block's source or destination is in the band, including a move crossing the edge while remaining in the band. Do not restrict the trigger to entering/leaving the band. Use the proposed movement's source/destination metadata for boundary dependencies, not a search from an interior piston. Multiple crossings require every touched boundary's old/new summary. Unknown reach or incomplete movement metadata defers offloading/consolidation rather than allowing an unverified cross-owner move.

### Minimum detector validation cases

Validate both coordinate orientations and negative chunk coordinates: unpowered dust crossing a boundary; strong versus weak power through one conductor; no power through two touching conductors; ascending dust with a changed support/clearance block; side-locked repeater; comparator reading a container through a conductor; observer watching a non-redstone border block; powered-but-not-yet-updated QC with a conductor above the piston; a piston move staying inside the band; breaking one of several paths; and an unknown mod rule. Assert both the resulting chunk edges and that no interior block scan occurred. These are required test cases, not a claim that runtime tests have passed.

## Whole-set ownership

A sub-server owns all chunks of a set or none. Sets may extend beyond its requested ownership radius; the radius is not permission to cut a contraption in half. A set with at most `redstone_takeover_max_chunks` distinct chunks is eligible (default 64); a larger set stays entirely on the real server. Equality passes the cap.

Overlapping player bubbles do not displace an existing set owner. Use [multi-client arbitration](multi-client-arbitration.md) for an existing whole set: first come, first served. Ordinary claims still require synced state and [handover](handover.md). One unmodded-player-occupied member pins the whole set for routine handover, moving or stationary. The distance-release exception compares the old owner's player chunk with every occupied member; only when all are strictly more than the configured default 12 chunks away can that exception transfer the whole set to the real server or another eligible sub-server. The incoming owner's distance does not release the old claim. Nearby empty chunks are not pinned merely by proximity. See [handover](handover.md#triggers) for all four exceptions and the square-distance rule.

## Topology changes and moving machines

A placement, break, or border-band piston move can merge sets, split them, or carry a flying machine into new chunks. The real server updates the set's chunk membership from the reported border topology at the completed-tick boundary, before the affected operation resumes. Recompute chunk-graph connected components for removals as well as additions; retain every chunk still connected by another path. Flag the resulting complete sets, add newly connected chunks, and remove obsolete membership only after checking remaining connections. Membership metadata is not itself an ownership grant. Do not leave a newly connected chunk with another owner while the operation proceeds.

If a pending operation would join differently owned sets, pause that affected operation, consolidate the complete resulting set onto the real server at a coordinated boundary, then resume the operation under one owner. Do the same when a set becomes too large for sub-server ownership. The real server is the coordinator and destination for required consolidation. Reuse [ownership handover](handover.md#transfer) for every source-owned part, with one reservation for the complete resulting set. Pause the triggering operation, prepare destination state while sources keep their existing simulation, collect readiness, then request each source's final stop at its next completed tick M. Different source histories retain their own identified tick/version boundaries; do not infer a common M from arrival time. Install every final state and queued outside input locally before committing all affected owner generations to the real server as one set. No part resumes the triggering operation early. After the whole-set commit, the real server continues each installed history at its next logical tick and resumes the operation under one owner. Chunks already server-owned use local handover roles, not self-addressed packets.

If preparation aborts, release the reservation, retain the prior committed owners, and resume any stopped source from its final state; keep the cross-owner triggering operation deferred until consolidation succeeds. A source failure uses [disconnect recovery](disconnect.md) before consolidation continues, rather than inventing missing state. Prepare snapshots/deltas before the final stop so the paused interval is minimal. These required consistency transfers are exceptions to routine unmodded-player occupied-chunk rule; ordinary overlap alone is not.

For growth that stays with one eligible owner, include every newly connected chunk before resuming the affected operation. A split changes membership but is not itself permission for another player to steal still-owned chunks. Claims and later releases continue through arbitration.
